# Задание 2. Мониторинг

### Мотивация

Внедрение мониторинга в сервис позволит улучшить следующие моменты:
- Быстрое выявление проблем и сбоев
- Оптимизация производительности
- Экономия ресурсов
- Анализ и принятие обоснованных решений о масштабировании, оптимизации и развитии.

Все это даст повышение качества сервиса, снижение затрат на инфруструктуру и улучшение производительности, а также повышение надежности и ставибольности сервиса.

### Выбор подхода к мониторингу
Поскольку сервис сейчас находится в облаке, где, вероятно, уже существует встроенная система мониторинга хоста, можно использовать эти метрики для анализа производительности сервера. Однако для удобства DevOps лучше объединить все данные в единую панель мониторинга. В этом случае я бы применил подход USE для сбора метрик сервера. 

Для остальных сервисов, таких как MES API, я бы использовал подход RED, который также можно применить к CRM API. Для СУБД необходимо собирать метрики QPS и latency.

### Опишите, какие метрики и в каких частях системы вы будете отслеживать

В данном случае я бы разделил метрики для инфраструктуры и бизнеса.

Инфраструктура:

**CPU % for shop API, CPU % for CRM API, CPU % for MES API** - для мониторинга производительности сервера
**Memory % for shop API, Memory % for CRM API, Memory % for MES API** - для мониторинга производительности сервера
**Disk % for shop API, Disk % for CRM API, Disk % for MES API** - для мониторинга производительности сервера

Чтобы пониманить о необходимости увеличения ресурсов.

**Size of S3 storage,Size of shop db instance,Size of MES db instance** - для отслеживания количества записей в базах данных

**Memory Utilisation for shop API, Memory Utilisation for CRM API, Memory Utilisation for MES API, Memory Utilisation for shop db instance, Memory Utilisation for MES db instance** - отслеживание использования оперативной памяти для инстансов, помогут отследить утечки памяти

Для разработчиков:

**Response time (latency) for shop API, Response time (latency) for CRM API, Response time (latency) for MES API** - отслеживание скорости обработки запросов

**Number of requests (RPS) for internet shop API, Number of requests (RPS) for CRM API, Number of requests (RPS) for MES API, Number of requests (RPS) per user for internet shop API, Number of requests (RPS) per user for CRM API, Number of requests (RPS) per user for MES API** - позволит понять количество реквестов, которые поступают в сервис, чтобы оценить общую нагрузку.

**Number of dead-letter-exchange letters in RabbitMQ, Number of message in flight in RabbitMQ** - помогут понять сколько запросов не получилось обработак и сколько запросов подвисло в очереди. Помогут в анализе данных для масштабирования. Или оптимизации монолитов.

Для бизнеса:
С этим у меня сложнее. Думаю, бизнесу важно понимать, сколько пользователей приходит в сервис и какова скорость обработки заказов. Также можно собирать конверсию, средний чек, количество просроченных заказов, удовлетворенность клиентов (если есть какая-то интерграция с сервисом саппорта).
