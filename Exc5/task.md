# Задание 5. Кеширование

### Проанализируйте диаграмму системы и её описание

Shop API

Закешировать статичные данные, которые не меняются во время работы системы. Справочные данные. Возможно данные о изделиях, которые уже были расчитаны до этого.

CRM API

Данные, часто используемые в CRM для отображения информации о клиентах и заказах.

MES API

Закешировать справочные данные. Данные которые применялись для расчета предыдущих заказов.

### Мотивация

В условиях роста нагрузки и обратной связи от клиентов, менеджеров и операторов внедрение кэширования поможет ускорить работу системы. Увеличится скорость повторного расчёта заказов, менеджеры будут быстрее получать данные о новых заказах, операторы — данные о заказах, а клиенты — информацию о заказах.

### Предлагаемое решение

Для клиентского кэширования можно использовать кэширование статики, так как у нас используется SPA-приложение.

Для серверного кэширования можно применить комбинацию подходов.

Между сервисами Shop, CRM и базой данных Shop можно использовать связку Read-Through и Write-Through, что позволит быстро получать данные из кэша при их наличии. Данные в кэше и базе данных будут консистентны. В качестве альтернативы для записи можно использовать подход Write-Behind, однако существует проблема ожидания обновления данных в БД.

Стратегии инвалидации:
- Invalidate on Write (приоритетная) - обеспечивает высокую консистентность данных
- TTL - может приводить к устаревшим данным в кеше

Для MES-сервиса также можно применить связку Read-Through и Write-Through. В качестве альтернативы для записи можно использовать подход Write-Behind, однако также потребуется ожидание обновления данных в БД.

Стратегии инвалидации:
- Invalidate on Write (приоритетная) - обеспечивает высокую консистентность данных
- TTL - может приводить к устаревшим данным в кеше

Подход Refresh-ahead представляется избыточным, так как данные в реальном времени в сервисе не меняются.
